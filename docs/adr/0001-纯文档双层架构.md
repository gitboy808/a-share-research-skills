# 纯文档双层架构承载跨会话经验

构建跨会话投研系统时，在"纯文档 / 文档+脚本 / 程序系统（数据库+定时任务）"中选择了纯文档，并将信息分为常驻层（每次新会话必读、体积设硬上限）与归档层（按需调取）。理由：核心痛点是信息架构（写什么、放哪、新会话先读什么）而非计算；代码与数据库引入维护成本和失效点，且会随积累把新会话的上下文预算吃光。常驻层硬上限（经验库 ≤50 条、当前判断单屏）是防止分层名存实亡的关键约束——没有它，系统会在一个月内退化成"从头读全部历史"。

## Considered Options

- 文档+轻量脚本（数据采集、校验、统计等）：现阶段暂缓而非永久排除；文档继续作为事实源，并保留未来增加脚本与定时调度的扩展边界。
- 程序系统（SQLite+定时任务+行情接口）：被否，维护成本偏离投研本身。

## Consequences

- 系统可靠性依赖 `AGENTS.md` 启动协议被每个会话遵守；协议本身需保持简短，否则新会话上下文预算被协议本身消耗。
- 教训、判断的质量由三态生命周期和版本链纪律保证，而非由工具校验。
- 当前盘前、集合竞价后和盘后流程均需用户触发；若未来要求无人值守运行，应另立 ADR 决定调度、失败恢复与数据快照边界。
